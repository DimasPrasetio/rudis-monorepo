# Deployment Standard — Docker image + deploy server

Every project generated by this standard deploys to a **deploy server**: a Docker host that runs
several apps under one fixed convention. No particular server is built into this skill — the
target (SSH host alias, optional server playbook, registry owner, domain) is configuration,
resolved per project in `knowledge/DEPLOYMENT.md` or per device in
`~/.config/rudis-monorepo/targets.json` (SKILL.md › Step 0b). When it is missing, ask the user.

This reference is the convention itself, plus what the scaffolder emits to satisfy it. **If the
target keeps its own playbook and it disagrees with this file, the playbook wins** — report the
drift and update this file; never "fix" the server to match the skill.

## Golden rules (non-negotiable)

1. **1 application = 1 image = 1 container.** A monorepo (web + api together) ships as one image
   and runs as one container. Never split one app across containers; never put two apps in one.
2. **MySQL runs once, at host OS level, shared.** Each app gets its **own database + own
   dedicated DB user**, granted on that database only. Never run a database container; never
   share a DB user across apps.
3. **Build in CI, run on the server.** GitHub Actions builds the image and pushes it to **GHCR**;
   the server only does `docker pull` + `docker compose up`. It **never** builds.
4. **Each app = one unique localhost port.** The container publishes to `127.0.0.1:<port>` only;
   the **host nginx** proxies a domain to it, TLS via `certbot`.
5. **Secrets live only in `~/<app>/.env`** on the server (`chmod 600`). Never committed, never
   baked into an image — injected at runtime via `env_file`.
6. **Firewall:** only 22/80/443 are public; 3306 is reachable only from the docker subnet
   (`172.16.0.0/12`). MySQL is never exposed to the internet.

## Step 0b — collect the deploy facts before scaffolding

| Fact | Scaffold flag | Where it comes from |
|---|---|---|
| App name (slug) | `--slug` | Short, lowercase letters/digits (`stokgudang`, `kasir`). Becomes `~/<slug>`, `<slug>-app`, `<slug>_db`, `<slug>_user`. Defaults to `--name` stripped to `[a-z0-9]`. |
| Localhost port | `--port` | The target's app registry / playbook if it keeps one, else the user — always confirmed on the server. |
| GHCR owner / repo | `--ghcr-owner`, `--repo` | The GitHub repo the image is built from: image = `ghcr.io/<owner>/<repo>` (lowercase). |
| SSH host / playbook / target | `--ssh-host`, `--playbook`, `--target` | The resolved deploy target. Written into `knowledge/DEPLOYMENT.md` and the release summary only. |
| Domain | `--domain` | Subdomain the user wants (e.g. `<app>.example.com`). May come later — leave it unset. |

How to look them up — **read-only**, and only when the user asked for deploy work:

```bash
ssh <ssh-host> 'cat <playbook>'   # only if the target keeps one: app registry + next free port
ssh <ssh-host> 'sudo ss -tlnp'    # confirm the port is really free
```

- Never read `~/<app>/.env`, `ADMIN_*` files, or anything else holding secrets — list keys at
  most (`sed 's/=.*/=<redacted>/'`).
- Never change the server from this skill without the user's explicit go-ahead: creating a
  database or user, nginx sites, certbot, `docker login`, deploying, or editing the playbook.
- No SSH access? Ask the user for the port. **Never guess a port** — a collision takes down
  another live app.

Facts not passed to the scaffolder are written as `__HOST_PORT__` / `__GHCR_OWNER__` markers;
`deploy.sh` refuses to run while any marker is left.

## Image (`infra/docker/Dockerfile`)

- Multi-stage; Node 22 for the web build. `npm ci` when `package-lock.json` is committed
  (commit it), `npm install` otherwise. Go projects must commit `go.sum` (`go mod tidy`).
- Runtime: non-root user **uid 10001**, `HEALTHCHECK` on `/readyz`, and **`ENTRYPOINT`, not
  `CMD`** — so `docker run <image> <args>` passes args to the app instead of replacing it.
- `infra/deploy/.env.production.example` ships inside the image (`/app/env.production.example`,
  the one exception in `.dockerignore`), so `deploy.sh` can check the server's `.env` against
  the version it is about to start.
- Go: `GOMEMLIMIT=400MiB` keeps the garbage collector under the compose memory limit (512M).
- Go: `DATA_DIR=/app/data`, owned by the app user — the one writable folder (below).
- The migration tool ships **inside the same image**, so the server migrates without any
  toolchain: Go → the `migrate` binary (copied from `migrate/migrate`) + `/app/migrations`;
  NestJS → Prisma CLI and engines in `node_modules` (`openssl` installed for Alpine);
  Express → not locked, nothing until the tool is chosen.
- Frontend is built as static assets into `/app/public`. Static serving is driven by the
  `PUBLIC_DIR` env var: the backend serves static files (with an SPA fallback to `index.html`)
  from that directory when it's set and exists; when `PUBLIC_DIR` is empty or the directory
  doesn't exist, static serving is skipped without error — this is the normal dev case, where
  the frontend is served by Vite instead. The Dockerfile sets `PUBLIC_DIR=/app/public`.
- The container listens on **8080**; the host side of the port mapping is the app's unique port.
- Image architecture is `linux/amd64` (the server).

## Readiness probe `/readyz`

Every backend exposes unversioned `GET /readyz` next to `GET /api/v1/health`. The image
`HEALTHCHECK`, the compose `healthcheck`, and `deploy.sh` all wait on it. The scaffold returns
200 unconditionally; once the database is wired, make it check the DB and answer 503 while
it is unreachable — that is what makes a failed deploy visible instead of "running".

## Default `docker-compose.yml`

```yaml
# LOCAL ONLY — builds from source for a quick check on your own machine.
# Production never builds: see infra/deploy/docker-compose.prod.yml (image-only).
services:
  app:
    build:
      context: .
      dockerfile: infra/docker/Dockerfile
    ports:
      - "8080:8080"
    # Copy .env.example to .env before running compose.
    env_file:
      - .env
    extra_hosts:
      - "host.docker.internal:host-gateway"
```

Do **not** generate this by default:

```yaml
services:
  mysql:
    image: mysql:8
```

## Production compose (`infra/deploy/docker-compose.prod.yml`)

What it must keep (the drift check asserts these):

- `image: ghcr.io/<owner>/<repo>:${IMAGE_TAG:?…}` — **no `build:`**, and `IMAGE_TAG` is
  **required** with no `latest` fallback. `deploy.sh` records the tag in `.env`, so a manual
  `docker compose up` stays on the last deployed version.
- `container_name: <slug>-app`, `restart: unless-stopped`, `env_file: .env`.
- `extra_hosts: ["host.docker.internal:host-gateway"]` — the way to reach the host MySQL.
- `ports: ["127.0.0.1:<port>:8080"]` — loopback only.
- Hardening: `read_only: true` + `tmpfs: /tmp`, `no-new-privileges`, a memory limit (512M by
  default on a shared small host), capped `json-file` logs, a `healthcheck` on `/readyz`.
  Anything the app writes needs an explicit volume owned by uid 10001. Go: the one volume is
  `./data:/app/data` (`DATA_DIR`) — uploads and anything else that must outlive a deploy;
  `deploy.sh` creates `~/<slug>/data` and hands it to uid 10001 (`sudo -n chown`) before the first
  start — or, where sudo is not allowed, warns and goes on (an app that stores files then refuses
  to start and says why). Uploads stream to it, never to `/tmp` (RAM in this container).
- A `migrate` service under `profiles: ["ops"]` (same image, migration entrypoint), run once
  per deploy by `deploy.sh`, never by `up`.
- **No** database service, ever.

## `deploy.sh`

`cd ~/<slug> && ./deploy.sh <git-sha>`:

0. **preflight** — no placeholder markers left; `.env` exists and is `chmod 600`;
   `APP_ENV=production`; `DB_NAME` set (warns when it isn't `<slug>_db`).
1. **pull** `ghcr.io/<owner>/<repo>:<git-sha>` (`latest` is refused — it can't be rolled back to),
   then check `.env` against the image's own copy of `.env.production.example`: every key must be
   present, and one whose example value is `<…>` must be filled. Nothing has changed yet when it
   refuses.
2. **backup** the app's database with `sudo -n mysqldump` into `~/<slug>/backups/pre-deploy.sql.gz`
   — one file, replaced each deploy (written beside the old one, checked with `gzip -t`, then
   moved). A failed dump fails the deploy. `SKIP_BACKUP=1` only for the very first deploy.
3. **migrate** via the `migrate` service (forward-only). Go: a database marked *dirty* stops the
   deploy; a database newer than the image's newest migration is a rollback, and migrate is
   skipped. `SKIP_MIGRATE=1` skips it by hand (the only way for NestJS/Express).
4. **up** `app` — after saving the outgoing container's log to `logs/<previous-tag>.log` (last 5
   kept) — and record `IMAGE_TAG` in `.env`.
5. **wait for `/readyz`** (max 120 s); on success remove this repo's images except the current
   and previous tag; on failure print logs and the rollback command.

`umask 077` from the first line: dumps and logs are owner-only from the moment they exist.
Rollback = `./deploy.sh <older-git-sha>`; it works across schema changes because releases follow
expand/contract (the generated `.claude/rules/database.md`). Restore and failed-migration recovery
are procedures in the project's `knowledge/DEPLOYMENT.md`.

## Backups

Two layers, and neither is optional:

| Layer | What | Where | Kept |
|---|---|---|---|
| Server, nightly | every `*_db` database on the host — a new app is included from its first night | `/var/backups/rudis/<db>/{daily,weekly,monthly}/` | 5 daily, 2 weekly (Sunday), 1 monthly (the 1st): 8 files at most; weekly/monthly are hard links to a daily file, so they take no extra space |
| Server, nightly | every app's data folder (`APPS_ROOT/<slug>/data`: uploads) | `/var/backups/rudis/<db>/files/{daily,weekly,monthly}/` | the same rotation, as `rsync --link-dest` snapshots: an unchanged file is a hard link to the previous snapshot, so a day costs only what changed |
| Per deploy | the state right before a migration | `~/<slug>/backups/pre-deploy.sql.gz` | 1, replaced each deploy |

The nightly job ships with this skill in `scripts/server/` and is installed **once per server**
(it changes the server: only with the owner's go-ahead). Paths below are the defaults; the
script reads `BACKUP_ENV` (default `/etc/rudis/backup.env`) and `BACKUP_ROOT` (default
`/var/backups/rudis`):

```bash
sudo install -D -m 700 rudis-backup.sh /opt/rudis/backup.sh
sudo install -m 644 rudis-backup.service rudis-backup.timer /etc/systemd/system/
sudo install -D -m 600 backup.env.example /etc/rudis/backup.env   # then fill in Telegram and APPS_ROOT
sudo systemctl daemon-reload && sudo systemctl enable --now rudis-backup.timer
sudo systemctl start rudis-backup.service && journalctl -u rudis-backup -n 20
```

It runs at 02:00 WIB as root (MySQL root through `auth_socket`), refuses to write when less than
15% of the disk is free (MySQL stops on a full disk, taking every app with it), checks each dump
(`gzip -t`, not empty), test-restores the newest into a scratch database on the 1st and compares
table counts, and sends failures — plus a weekly "all fine" — to Telegram
(`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` in `/etc/rudis/backup.env`). Backups live on the
same disk as the databases: a lost server loses them too. Off-site copies are not part of this
job — add them per server if the owner wants them.

## Environment

`infra/deploy/.env.production.example` lists the production keys without values. On the
server it becomes `~/<slug>/.env` (`chmod 600`). Key conventions:

```env
# Go
APP_ENV=production
DB_HOST=host.docker.internal
DB_PORT=3306
DB_USER=<slug>_user
DB_PASSWORD=<openssl rand -hex 24>
DB_NAME=<slug>_db
DB_DSN=<slug>_user:<password>@tcp(host.docker.internal:3306)/<slug>_db
```

```env
# NestJS / Express
APP_ENV=production
DB_HOST=host.docker.internal
DB_PORT=3306
DB_USER=<slug>_user
DB_PASSWORD=<openssl rand -hex 24>
DB_NAME=<slug>_db
DATABASE_URL=mysql://<slug>_user:<password>@host.docker.internal:3306/<slug>_db
```

- Generate passwords as **hex** (`openssl rand -hex 24`): they go inside a DSN/URL unescaped.
- `CORS_ALLOWED_ORIGINS` is the explicit public origin, never `*`.
- `TRUSTED_PROXIES=172.16.0.0/12,127.0.0.1/32`: the host nginx reaches the container from the
  docker bridge. Without it, every user looks like one IP and per-IP rate limiting locks
  everyone out at once.
- `APP_TIMEZONE=Asia/Jakarta` (Go): where business dates and calendar schedules are counted.
  A branch in WITA/WIT keeps its own zone in the organization module.
- The host MySQL must log row-based (`binlog_format=ROW`, MySQL 8's default): the kernel's task
  queue claims rows with `SKIP LOCKED`, which statement-based replication cannot replay safely.

Database + user, created once on the host MySQL. Read the version first — it decides the
account plugin, by the same table as on a developer's machine
([local-database.md › The account plugin](local-database.md#the-account-plugin-read-the-version-first)):

```bash
sudo mysql -e 'SELECT VERSION();'
```

On MySQL 8.0, 8.4 or 9.x (MariaDB: `IDENTIFIED BY '<random-hex>'`):

```sql
CREATE DATABASE <slug>_db CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER '<slug>_user'@'172.%' IDENTIFIED WITH caching_sha2_password BY '<random-hex>';
GRANT ALL PRIVILEGES ON <slug>_db.* TO '<slug>_user'@'172.%';
FLUSH PRIVILEGES;
```

`'172.%'` because connections arrive from the docker bridge. `caching_sha2_password` because an
account created `WITH mysql_native_password` stops the app the day the server moves to 8.4
(`Error 1524` — why, in the same table).

### Drivers on the docker bridge, without TLS

The app reaches MySQL over plain TCP. `caching_sha2_password` then needs, on a *full*
authentication — the first login, and the first after every server restart or `FLUSH
PRIVILEGES` (the cache is in memory) — either TLS or the server's RSA public key. The server
has a key pair by default (`caching_sha2_password_auto_generate_rsa_keys=ON`) but sends the
key only when the client asks. The scaffold's clients ask by themselves; none needs a DSN
option, and none turns TLS on unless told to:

| Backend | Client | On full authentication without TLS |
|---|---|---|
| Go app | go-sql-driver/mysql v1.8.1 | requests the key, sends the password RSA-encrypted (`auth.go`) |
| Go migrate (`migrate/migrate:v4.18.1`) | go-sql-driver/mysql v1.5.0 (its `go.mod`) | same |
| NestJS (and `prisma migrate deploy`) | Prisma 5 → quaint → mysql_async | same (`continue_caching_sha2_password_auth`) |
| Express, if it uses `mysql2` (or Knex/Drizzle on it) | mysql2 ≥ 2.0 | same |

Where it does **not** work as is:

- **`mysql` (mysqljs)**: no `caching_sha2_password` support at all — an Express app must not
  use it (nor Knex `client: 'mysql'`); use `mysql2`.
- **`mariadb` (Node connector)**, and so **Prisma 6/7 with `@prisma/adapter-mariadb`**: refuses
  with `ER_CANNOT_RETRIEVE_RSA_KEY` unless given `allowPublicKeyRetrieval: true` (or
  `?allowPublicKeyRetrieval=true` in the URL), or `cachingRsaPublicKey`, or TLS. Set it when a
  project moves to that driver.

`ERROR 2061 … Authentication requires secure connection` is the message of libmysqlclient
tools — the `mysql` CLI, `mysqldump` — when TLS is off (`--ssl-mode=DISABLED`, or a server
without SSL) and neither `--get-server-public-key` nor `--server-public-key-path` is given. It
never comes from the app's drivers. To test the account from a container with the CLI, add
`--get-server-public-key`. A test that follows an earlier successful login passes through the
cache and proves nothing about the RSA path — test right after creating the account.

A key fetched on the fly protects the password from a passive listener, not from someone who
can rewrite traffic; on the bridge inside one host that is the accepted trade-off. Across a
network, use TLS.

### Accounts created with `mysql_native_password`

Apps set up before this rule have `<slug>_user` `IDENTIFIED WITH mysql_native_password`:

```bash
sudo mysql -e "SELECT user, host, plugin FROM mysql.user WHERE plugin = 'mysql_native_password';"
```

- **On MySQL 8.0 leave them alone.** The plugin still works there; changing a running app's
  account buys nothing until the server moves.
- **Before the server moves to 8.4 or 9.x**, switch each one while it is still on 8.0 — the
  owner's go-ahead first, one app at a time, keeping the password the app already connects
  with, so `.env` does not change. In the app's folder on the server (the subshell stops at
  the first step that fails):
  ```bash
  cd ~/<slug> && (
    set -eu
    C="docker compose -f docker-compose.prod.yml"
    # The password inside the DSN the app reads — not DB_PASSWORD, which nothing reads — and a
    # read-only command that signs in the way the app does, picked by backend:
    if grep -q '^DB_DSN=' .env; then                                        # Go
      PW=$(sed -n 's/^DB_DSN=[^:]*:\([^@]*\)@.*/\1/p' .env | tr -d '\r"')
      CHECK="$C --profile ops run --rm migrate version"
    else                                                                    # NestJS / Express
      PW=$(sed -n 's|^DATABASE_URL="\{0,1\}mysql://[^:]*:\([^@]*\)@.*|\1|p' .env | tr -d '\r"')
      CHECK=""
      grep -q prisma docker-compose.prod.yml && CHECK="$C --profile ops run --rm --entrypoint node migrate node_modules/prisma/build/index.js migrate status --schema apps/api/prisma/schema.prisma"
    fi
    [ -n "$PW" ] || { echo "no password found in .env"; exit 1; }
    printf "ALTER USER '<slug>_user'@'172.%%' IDENTIFIED WITH caching_sha2_password BY '%s';\n" "$PW" | sudo mysql
    sudo mysql -N -e "SELECT plugin FROM mysql.user WHERE user = '<slug>_user' AND host = '172.%'"
    # ALTER USER emptied the account's cache: this is a full authentication, as the app's will be.
    if [ -n "$CHECK" ]; then $CHECK; else echo "no migrate service: check the app's own queries after the restart"; fi
    $C restart app
    for i in $(seq 60); do curl -fsS http://127.0.0.1:<port>/readyz >/dev/null && exit 0; sleep 2; done
    echo "/readyz did not answer within 120 s"; exit 1
  )
  ```
  `printf` is a shell builtin and `sudo mysql` reads stdin, so the password reaches neither a
  process list nor the shell history. The migrate step is the real test: only the Go `/readyz`
  queries the database — NestJS and Express answer it without one until the app wires a check,
  and Express has no migrate service (use whatever query the app runs). `prisma migrate
  status` exits 1 while migrations are pending or before the first one exists, so run the block
  after a completed deploy — and if that is why it stopped, the account is fine: check the app
  log before any undo. If the
  server refuses the same password (`password_history`), the block stops before anything
  changed.

  **Undo** (8.0 still has the plugin) — when a step after the `ALTER USER` failed:
  ```bash
  cd ~/<slug> && (
    set -eu
    if grep -q '^DB_DSN=' .env; then
      PW=$(sed -n 's/^DB_DSN=[^:]*:\([^@]*\)@.*/\1/p' .env | tr -d '\r"')
    else
      PW=$(sed -n 's|^DATABASE_URL="\{0,1\}mysql://[^:]*:\([^@]*\)@.*|\1|p' .env | tr -d '\r"')
    fi
    [ -n "$PW" ] || { echo "no password found in .env"; exit 1; }
    printf "ALTER USER '<slug>_user'@'172.%%' IDENTIFIED WITH mysql_native_password BY '%s';\n" "$PW" | sudo mysql
    docker compose -f docker-compose.prod.yml restart app
  )
  ```
  Find out why before trying again. Upgrade the server only when the first query returns no
  app account.
- **Already upgraded, app down with `Error 1524`**: run the switch above. `ALTER USER` sets the
  new plugin and password itself; it does not sign in through the old plugin. On 8.4, starting
  MySQL with `mysql_native_password=ON` is a stopgap that 9.0 no longer offers
  ([local-database.md › Error 1524](local-database.md#error-1524-plugin-mysql_native_password-is-not-loaded)).

## CI → GHCR

- `ci.yml` (name **`ci`**): Go → `go build/vet/test` in `apps/api`; all stacks →
  install + `build:web` (+ `build:api` for Node backends).
- `release-image.yml`: `workflow_run` on `ci` **completed + success + push to `main`**, checks
  out that exact `head_sha`, builds `linux/amd64`, pushes `:<git-sha>` and `:latest`, and prints
  the deploy command in the job summary. Image name = `ghcr.io/` + the lowercased repository.
- New GHCR packages are **private**. The server needs either a `read:packages` token
  (`docker login ghcr.io`) that can see the package, or the package set to Public.

## Host nginx + TLS

- One site per app: `/etc/nginx/sites-available/<slug>`, `server_name <domain>`,
  `proxy_pass http://127.0.0.1:<port>` with `Host`, `X-Real-IP`, `X-Forwarded-For`,
  `X-Forwarded-Proto` headers.
- **Never `default_server`** — only one is allowed per `:80`, and on a shared host another app may already hold it.
- Go: a second `location ~ ^/api/v1/[^/]+/stream` passes server-sent event streams with
  `proxy_buffering off` and `proxy_read_timeout 1h` (the generated `infra/nginx/nginx.conf`
  has it). An app upgraded to kernel 6 copies that block into its site and reloads nginx.
- Point the domain's DNS A record at the server and check it resolves there **before** running
  `sudo certbot --nginx -d <domain>`.
- HSTS only after certbot has installed TLS.

## Why the rules look like this (the incident behind each rule)

| Rule | Incident it prevents |
|---|---|
| `ENTRYPOINT`, not `CMD` | `docker run <image> migrate up` tried to exec a binary named "migrate" and left migrations half-applied |
| Migrate with the migration CLI, not the app's DB pool | multi-statement migrations failed on a pool without multiStatements, leaving `schema_migrations` dirty |
| `IMAGE_TAG` required, no `latest` | a manual `compose up` silently fell back to an older local `latest` |
| GHCR access checked before deploy | a new package was private and the server's token couldn't pull it |
| `TRUSTED_PROXIES` covers the docker bridge | all users shared one IP and hit the login rate limit together |
| `SELECT VERSION()` before `CREATE USER`; new accounts `caching_sha2_password` | an account created `WITH mysql_native_password` (the earlier rule, written against `ERROR 2061` — a `mysql` CLI message, not one of the app's drivers) answers `Error 1524` once the server runs 8.4 |
| No `default_server` | `nginx -t` failed with "duplicate default_server" |

## Never do

- Dockerize MySQL / add a database container or compose service.
- Build images on the server (`docker build`, `compose up --build`, a `build:` key in prod compose).
- Publish 3306, or publish the app on `0.0.0.0`.
- Run one app across several containers, or several apps in one container.
- Reuse a DB user across apps, or grant beyond the app's own database.
- Commit `.env`, or bake secrets into an image.
- Deploy `latest`.
